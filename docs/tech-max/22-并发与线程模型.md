> 源码基准：`src/utils/KeyedTaskScheduler.h/.cpp`、`src/utils/Live.h`、`src/Bootstrap/RuntimeSettings.cpp`（mapMessageExecution）、`src/Bootstrap/ConfigReloader.h/.cpp`、`src/main.cpp`、`src/Memory/MemoryService.h/.cpp`、`src/Log/Log.cpp`、`src/Perception/ReflectionService.h/.cpp`、`Library/httplib/httplib.h`（线程池宏）。本卷将分散于[卷01 §5](01-项目全景.md#5-运行时的线程全景)、[卷03](03-启动与生命周期.md)、[卷07](07-消息调度与路由.md) 的线程内容收敛为一处，并补齐同步原语与数据竞争防护的完整清单。

## 0. 设计原则

1. **固定数量的小线程 + 一个弹性消息执行器**：除消息 worker 外，其余线程全部是常驻单线程，各自只负责一类 I/O 或轮询；数量在启动时确定，运行期不变。
2. **并发粒度是"用户"而非"消息"**：同一用户严格串行（会话状态天然无竞争），不同用户并行，由 `KeyedTaskScheduler` 保证。话题会话的 judge/轮次任务以 **群 lane**（groupId | 0x8000&apos;0000&apos;0000&apos;0000 高位标志避免与 user_id 撞车）入同一调度器：同群串行、跨群并行（意志层 v2 起，2026-09-16）。
3. **共享可变状态极小**：跨线程共享的可变量只有进程级 `running` 原子量、组合根的活值集合 `LiveSettings`（ADR-023）与各 Store 内部数据；业务对象之间以构造引用 + 值快照通信。每个 `Live<T>` 由重载入口的应用函数整份替换快照指针，读者只拿不可变快照：L1.a–L1.f 起 chat、三个模型端点、voice、memory、搜索/抓取/代理、群聊开关、`affect.enforce`、瞥视预算的读者在各自一次操作开头取快照。语音总开关 `globalVoice` 也是其中一个 `Live<bool>`，管理员命令（`AdminControlAction`）与配置重载都会 `set` 它（L1.c；此前是 main 栈上的 `bool`）。

**传输循环内的周期工作（不新增线程）**：WS 模式每秒调用一次 `DeliveryReceiptRegistry::sweep()`，把 60s 未兑现的业务投递回执记为 `unknown`（R0.2）；HTTP 模式由响应体同步回报，不需要清扫。

**面板线程的内部并发**：`ConfigPanelServer::run` 是 1 个 Klein 线程，但 vendored cpp-httplib v0.53.1 在 `listen()` 内部维护自己的 ThreadPool——基准线程数 `CPPHTTPLIB_THREAD_POOL_COUNT = max(8, CPU逻辑核数−1)`，上限为基准的 4 倍（`*_MAX_COUNT`），空闲 3 秒回收（`*_IDLE_TIMEOUT`）。该池为 httplib 库内部行为，Klein 未显式配置，做线程数预算时需计入。推送门线程自 2026-10-25 起运行时搁置（见 technical-design §16.4），因此当前不再有第二个同规格池；恢复后会再增加一个。

**进程线程总数的近似边界**（设 CPU 逻辑核数为 N）：

- 最小：配置 `worker_threads=1`、关闭 webui 与观察通道、服务器模式 WS（推送门已搁置）→ 主线程 1 + worker 1 + 传输 1 + 定时 1 + 记忆 1（记忆库能打开就启动，与 `memory.enabled` 无关）+ 回想 1 + 日志 1 = **7 个**。
- 默认最大（未配置 worker_threads、启用全部可选功能、http 传输；推送门当前搁置不计）：worker 最大 `4N` + 主线程 1 + 传输 2（含 API sender）+ 定时 1 + 记忆 1 + 瞥视 1 + 回想 1 + 面板 1 + httplib 内部最多 `4×max(8, N−1)`（仅面板池）+ 日志 1。以 N=8 为例：32+2+1+1+1+1+1+1+32+1 ≈ **73 个**（httplib 池通常远低于上限；恢复推送门后约为 106 个）。

## 2. 消息执行器：动态线程池的设计（核心问题的直接回答）

**结论：是动态（弹性）线程池；配置 `chat.worker_threads` 后退化为固定线程池。**

### 2.1 尺寸规则（RuntimeSettings.cpp `mapMessageExecution`）

```
配置了 chat.worker_threads = N（范围 [1,256]）：
    initial = N，max = N，dynamicScaling = false        ← 固定池，永不伸缩
未配置：
    N0 = std::thread::hardware_concurrency()（取 0 时按 4）
    initial = N0                                        ← 最小（也是常驻基础数）
    max     = N0 × 4（带溢出保护）                       ← 最大
    dynamicScaling = true                               ← 弹性池
```

构造时统一钳制下限：`initial ≥ 1`、`max ≥ initial`、`maxPendingMessages ≥ 1`、`workerIdleSeconds ≥ 1`。因此**绝对下限是 1 个 worker，绝对上限是 256 个**（受配置字段范围约束）。

### 2.2 扩容与缩容条件（KeyedTaskScheduler）

| 行为 | 触发条件 | 动作 |
| --- | --- | --- |
| 扩容 | `submit()` 时 `dynamicScaling && liveWorkers < max`，且 `readyKeys.size() > idleWorkers`（就绪 lane 数超过空闲 worker） | 新增 `min(缺口, max−liveWorkers)` 个 worker。**扩容仅由 submit 驱动**，不在后台自我探测 |
| 缩容 | 仅对超出 `initial` 的弹性 worker：在 `workerIdleSeconds`（默认 30s，配置范围 [1,3600]）内未等到任务即自行退出 | `liveWorkers` 减一、置 finished 标志；线程对象由下一次 `submit` 时的 `reapFinishedWorkers()` join 回收 |
| 基础 worker | 不超过 `initial` 的部分 | 无限等待（`cv.wait`），永不超时退出——保证池的最小常驻规模 |

### 2.3 与"固定池"的取舍

弹性部分解决的是**尾延迟**：低负载时只保留 N 个常驻线程；突发负载（多用户同时提问）时按就绪 lane 数瞬时扩到 4N。代价是弹性 worker 退出/回收引入少量簿记复杂度（finished 标志 + reap）。选择 4 倍上限的依据：worker 主要时间阻塞在模型 HTTP（数百 ms 到数十 s），`4×` 允许单核上有多个在途外部请求，同时限制最坏线程数量。

### 2.4 背压（池外兜底）

池本身无界排队能力由 `maxPendingMessages` 限制（`MessageExecutionOptions::kMaxPendingMessages`，程序内部定值 1024，**不开放给配置文件与面板**）：`outstandingTasks ≥ 上限` 时 `submit` 返回 `Full`，主循环直接回"系统繁忙"（不经过调度器）。注意计数含"正在执行"的任务，是总量上限而非纯队列长度。并发参数中唯一暴露给配置的是线程数：`chat.worker_threads` 配置了则固定该数并关闭动态伸缩，缺省时按 `hardware_concurrency()`（至少 4）动态伸缩、上限 4 倍（§2.1）。

## 4. 锁的嵌套关系与持锁时长

存在嵌套的三条链（外层 → 内层；配置重载与回想写认识另有两条，见下）：

```
USS.mutex_message → ConversationStore.dbMutex        （appendMessage：锁内写穿）
ReminderService.queueMutex → ReminderStore.dbMutex   （cancel/popDue：锁内删行/滚动）
KeyedTaskScheduler.mutex（无嵌套，任务在锁外执行）
```

配置重载另有一条链（2026-11-15，ADR-023）：`ConfigReloader.reloadMutex → ConfigSnapshotStore.reloadMutex → ConfigSnapshotStore.mutex`；应用阶段在 `ConfigReloader.reloadMutex` 内依次调用各 `Live<T>::set`，取的是叶子锁。这条链里没有业务锁；调用方是面板的请求处理线程（保存配置）与消息 worker（`#刷新配置文件` 命令或 `admin_control` 工具）。`Live<T>` 的锁不与任何业务锁嵌套——持有期间只复制或交换一个 `shared_ptr`，不取别的锁、不调用外部代码，所以无论调用方当时持有什么锁都不会形成环。`set` 的调用方：重载入口的应用函数，以及 `AdminControlAction`（`#激活语音/#冻结语音`，只改语音总开关，L1.c）。`get` 都在业务锁之外：USS 先取 chat 快照再拿 `mutex_message`（L1.a）；记忆后台线程每轮先取 memory 快照再拿 `queueMutex`（L1.d）；瞥视 worker 在队列锁之外、每张图开头取预算（L1.f）；`EngagementService::runTurn` 在拿会话锁之前取 `enforce`（L1.f）；其余读者（Voice、两个模型适配器、搜索与抓取、Message）取快照时不持任何 Klein 锁。

回想写认识时另有一条（经历层 E3）：`KnowledgeLedger.mutex → DecisionStore.mutex`——`apply` 在账本锁内经依据核对器 `evidenceCheckerFor` 查决策库，这是唯一一处存储锁套存储锁；`DecisionStore.mutex` 是叶子锁（持有它时除日志队列锁外不取别的锁），可以在 `KnowledgeLedger.mutex` 之内被获取，决策库从不回调账本，互斥锁层面没有反向路径。回想 worker 只在取任务与回写已排队集合时持 `queueMutex`，`runNow`（读决策库、群缓冲、账本，调模型，写反馈与账本）都在它之外。

**已知风险：SQLite 层的隐式反向依赖。** 账本与决策库是同一个 SQLite 文件上的两个连接。`KnowledgeLedger::apply` 先在账本锁内 `BEGIN IMMEDIATE` 拿到库文件的写锁，再在事务里经依据核对器取 `DecisionStore.mutex`；写决策 / 执行 / 反馈记录的线程则先持 `DecisionStore.mutex`，再要同一个库文件的写锁——两边顺序相反。两个连接都设了 `busy_timeout(5000)`，所以不会永久卡死：最坏情况下写记录的一方等满 5 秒得到 `SQLITE_BUSY`、写入失败（那条记录丢失）并释放 `DecisionStore.mutex`，账本一方随后继续。窗口只在 `apply` 的校验循环里（一次至多 `KnowledgeRules::kMaxChangesPerRun` 条改动，每条的每个依据各查一次决策库）。

无全局锁序文档，但嵌套方向固定（业务锁总是先于存储锁获取；唯一的存储锁套存储锁是上面的账本 → 决策库，`DecisionStore.mutex` 是叶子锁），互斥锁层面不存在反向获取路径；SQLite 写锁的反向依赖见上一段。持锁时长分析：

- **最长的持锁路径**是 `USS.appendMessage`：一次内存 push + 一条 SQLite INSERT（busy_timeout 5s 内）。模型 HTTP（秒级）**不持任何 Klein 锁**——`buildChatRequest` 返回值拷贝后立即释放锁，这是"多用户互不阻塞"的关键。
- 调度器互斥量只在入队/取任务/完成回写三个临界区短暂持有，任务体在锁外运行。

## 5. 无共享设计（避免加锁的手段）

| 手段 | 位置 |
| --- | --- |
| 值快照跨线程传递 | `ChatCallBundle`（history 拷贝出锁）、`shared_ptr<InboundMessage>` 进任务 lambda |
| 请求副本隔离 | 工具轮次的临时 history 只改请求副本，不碰 Person |
| 每请求独立 curl 句柄 | 各适配器每次调用 `curl_easy_init`，句柄不跨线程共享 |
| 不可变共享 | `ToolRegistry` 注册后只读；`ConfigSnapshot` 以 `shared_ptr<const>` 发布，读者无锁；活值 `Live<T>::get()` 交出 `shared_ptr<const T>`，拿到后无锁使用，替换是整份换指针，正在进行的操作继续用旧快照（ADR-023） |
| 互斥热重载 | `ModelRegistry` 内部 vector 由互斥锁保护：读者加锁取 ChatModel 拷贝，面板线程 `reload()` 在锁外构建新表、锁内整体交换——在途 LLM 调用持有的是拷贝，不受重载影响 |
| 线程内局部状态 | 调度器 lane 的串行执行使同一用户的 Person 无并发写（锁只防跨用户的全表操作） |

## 6. 数据竞争防护要点

1. **停止信号的传播**是单写多读：main 写 `running`，所有线程只读；curl progress callback、各线程循环条件、看门狗均观察同一原子量。取消语义从"原子量"到"CURLE_ABORTED_BY_CALLBACK"到"响应 cancelled 标志"逐层上抛（[卷05 §7](05-网络与OneBot传输层.md#7-curl-请求控制curlrequestcontrol)、[卷11 §5.3](11-模型调用层.md#53-httppost134211-行两个适配器几乎相同)）。
2. **记忆 epoch**（`userEpoch`，queueMutex 保护）实现"删除使在途异步写失效"：提取前后及逐条落库前三次校验（[卷14 §1.4](14-长期记忆系统.md#14-processbatch-与-epoch-失效机制)）。
3. **语音附件生命周期**靠"入队即终态"约定消除竞态：文件由发送线程创建、由传输线程在投递落定后删除，中间无其他访问者（[卷05 §2](05-网络与OneBot传输层.md#2-共享-ws-会话onebotwebsocketsessioncpp服务器客户端模式复用)）。
4. **日志线程**是唯一写文件者，业务线程只入队；`localtime` 等非线程安全函数仅在展示层使用（[卷18](18-支撑模块.md) 已知边界）。
5. **瞥视视觉就绪的状态日志**（L2.b）：`GlanceService` 用原子量 `lastVisionReady` 记上一次判定，`enqueue` 时就绪状态变化才打一次日志，多个 worker 同时入队不会重复打。
6. **语音总开关**：L1.c 之前它是 main 栈上的 `bool`，经引用交给 `VoiceModeAction`、`AdminControlAction` 与 `Message`，管理员命令在一个 worker 线程写、其他 worker 线程读，没有任何同步（数据竞争，实际后果是读到旧值）。L1.c 改为 `Live<bool>` 后读写都经它的互斥量。
7. **已知残余边界**：`ComputerStatus`/`CloudMusicID` 等低频路径的 curl 句柄无取消挂接；httplib 内部线程池规模不受 Klein 配置控制；`Log::getCurrentTime` 在多线程 INFO 下并发调用 `localtime`（展示无害）。群聊材料每行的时刻与事实卡的日期时刻经 `utils/LocalDate.h` 的 `localTimeOf`（`localtime_r`/`localtime_s`，2026-11-16 起；此前会话轮与 @ 群背景各有一份调用 `std::localtime` 的 `formatClock`）。

## 7. 生命周期时序（与卷03 §11 互补的并发视角）

退出链的顺序本质是**依赖方向的反向释放**：

```
running=false（广播）
→ 调度器 shutdown：新的 submit 拒绝；在途任务可能正在进行模型 HTTP，
   由 curl 取消机制在秒级内收敛 → join 全部 worker
→ 瞥视服务 shutdown（必须在 worker 全部退出后：observe 会 enqueue；丢弃 pending，进行中的视觉 HTTP 已被 curl 取消，返回后不写回）
→ 记忆服务 shutdown（必须在 worker 全部退出后：在途任务可能 enqueueTurn）
→ 回想服务 shutdown（丢弃排队的群、join 回想 worker；进行中的模型调用已随 running=false 取消；在 pollingThread 之前收，之后定时线程上的 pump 是空操作）
→ 定时 → 传输（内部先 join API sender）→ 面板（看门狗 stop）
→ 日志 shutdown（最后：前述所有阶段的收尾日志都要落盘）
```

第二次信号直接 `std::_Exit(128+signal)`，放弃全部未完成写入（[卷03 §2](03-启动与生命周期.md#2-信号处理maincpp6774-244245)）。

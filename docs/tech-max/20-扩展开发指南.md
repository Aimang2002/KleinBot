# 卷 20 · 扩展开发指南：加功能时的逐文件操作手册

> 本章回答"新增某类功能时应修改哪些文件、按何种顺序操作"。每节均附检查清单。动手之前先读[设计哲学](../design-philosophy.md)：它决定一个功能该不该加、该放在哪，本章只回答“怎么放”。开始前请先阅读[卷01 §7](01-项目全景.md#7-模块依赖方向红线) 的依赖红线。

## 0. 通用前置

- 构建：新 `.cpp` 丢进 `src/<模块>/` 即被 GLOB 收编，**无需改 CMakeLists**（`CONFIGURE_DEPENDS` 自动发现）。新目录也行（include 路径已覆盖 `src/` 根与多数子目录，用相对 include 即可）。
- 提交规范：`feat:/fix:/refactor:/test:/docs:/chore:` + 中文短述；不主动 commit/push。
- 每类扩展的默认路径都遵循 ADR-014：**业务能力写成 Action，需要 `#命令` 加 Command 适配器，需要自然语言触发加 ActionTool**。

## 1. 新增一个模型工具（最常见）

例：加一个"查询天气"工具。

```
1. src/Action/WeatherAction.h/.cpp     ← 业务逻辑（推荐走 Action）
   - descriptor()：name="get_weather"、description（给模型的使用时机说明，认真写）、
     parameters_schema（JSON Schema，required/enum/minMax 齐全——模型按它产参数）
   - execute(arguments, context)：校验参数（错误返回中文"错误：…"文本，terminal=false
     便于模型纠正重试）；调外部 API；结果 dump 成 JSON 文本返回
2. （可选）仿照 src/WebSearch/ 建立独立 Provider 模块——外部 API 协议不应写入 Action，
   学 TavilySearchProvider：接口 + 构造注入 HttpPost 函数（测试可用假 HTTP）
3. main.cpp：
   - 栈上构造 Action（依赖以引用/回调注入，参考 WebFetchAction 的 Distiller 注入）
   - tools.registerTool(make_unique<ActionTool>(action));
   - （可选）在 ChatService.cpp 的 system_prompt 组装处按工具名追加使用规则段
     [卷10 §3 的模式——只加稳定内容]
4. 配置（可选）：SchemaConfig.h 加 WeatherSchema + ConfigLoader.cpp 解析段 +
   RuntimeSettings.h/.cpp 映射 + 规则表 ConfigRules.cpp 每个键一行（回答怎么生效，见 §6 第 6 项）
   + config.example.json + 卷04 文档
5. 测试：tests/ActionTests.cpp 补用例（Fake 依赖）
```

检查清单：□ 工具名全局唯一 □ 失败返回错误文本而非抛异常 □ 外部结果标注"不可信数据"语义 □ schema 与 description 一致 □ 不写 SQL/OneBot 码。

## 2. 新增一个 # 命令

```
1. src/Command/XxxCommand.h/.cpp
   - canHandle(message)：匹配字段是去空白后的 plain_text（卷08 §3）
     ——前缀型用 utils::check_command_exists；全等型 == 比较即可（群聊/私聊一致）
   - execute(ctx)：参数从 ctx.data.plain_text 提取（CP_split）；业务委托给 Action 或 USS；
     返回 CommandResult{语义消息}
   - requiresAdmin() 按需
2. main.cpp：commandRegistry.registryCommand(make_unique<XxxCommand>(…));
3. #帮助 文案：src/Command/HelpText.h
```

## 3. 新增一个 Action（仅命令入口，暂不给模型）

同 [§1](#1-新增一个模型工具最常见) 第 1 步，然后在 main.cpp 构造 + Command 适配器（参考 QueryModelCommand 的写法）。**注意 Action 的 terminal 默认 true、ToolResult 默认 false**，两侧语义不可混淆（[卷09 §2](09-Action与Tool体系.md#2-action-接口actionh)）。

## 4. 接入新的模型供应商（API 标准）

```
1. src/ModelApiCaller/NewStandard/NewStandard.h/.cpp : public LLMPort
   - request_chat/vision/image 三个方法全实现（不支持的返回 code=-1 + 错误说明，
     参考 AnthropicStandard::request_image）
   - http_post 直接抄 OpenAIStandard.cpp §5.3（重试/取消/错误 envelope 语义保持一致）
   - 解析器把供应商 JSON 映射回统一 ChatResponse（finish_reason 对齐 "tool_calls" 等约定）
   - 载荷构造若与 OpenAI 同构 → 直接复用 ChatPayloadBuilder；否则加新工厂函数
2. src/ModelApiCaller/Dock.hpp 构造函数里 registryLLM.emplace("NewStandard", …)
3. ModelsName.json 的 APIStandard 字段填新标准名（大小写敏感）
4. WebUI 面板 validateModelRegistry 的白名单加名字（ConfigPanelServer.cpp）
5. 测试：响应解析器做成可测（参考 AnthropicStandard 把 chat_json_parse 公开）
```

**注意"三次重复再抽象"原则**：目前 http_post 已存在两份实现（OpenAI/Anthropic），第三个供应商出现时再提取公共层（[卷01 §7](01-项目全景.md#7-模块依赖方向红线) 的既定决策，不宜提前抽象）。

## 5. 新增传输协议（如 Milky）

```
1. 新建 src/Protocol/Milky/：EventDecoder（→InboundMessage）+ MessageEncoder（←OutboundDelivery）
   ——语义队列不动（这正是当初分层的目的）
2. 新建 src/Network/MilkyTransport.*：实现收发循环（参考 MyWebSocket 的
   "外层 while(running) + 失联等待重连"骨架）
3. TransportConfig：加 MilkyConfig 结构 + TransportMode 枚举值 + transportModeName
4. Configuration：TransportProfileSchema 新 type 分支 + Bootstrap mapTransport 映射
   + 规则表 ConfigRules.cpp 的 communication.active_profile.* 行（新字段加一行）
5. main.cpp 的 switch(transportConfig.mode) 加分支
6. 契约测试：tests/transport_contract_test.py + TransportContractDriver.cpp 加用例
```

## 6. 改配置项 / 加配置节

**全链路 10 处，一处不漏才算改完**（漏一处就会出现"面板看不见/用户照抄收到未知字段警告/文档与代码不符"这类半成品状态）：

| # | 落点 | 漏掉的后果 |
| --- | --- | --- |
| 1 | `src/Configuration/SchemaConfig.h` | 加 Schema DTO 与 `SchemaConfig` 成员 |
| 2 | `src/Configuration/ConfigLoader.cpp` | 顶层 `unknownFields` 白名单 + 节内白名单 + 解析与校验诊断（区间/派生态） |
| 3 | `src/Configuration/ConfigTemplate.cpp` | **首跑骨架缺该键 → 面板对应分区根本不渲染**（T7c 实翻车点） |
| 4 | `config.example.json` | 用户照抄示例缺节；**顺带核对示例里没有已删除的过期键**（用 `--check-config` 验未知字段为 0） |
| 5 | `src/Bootstrap/RuntimeSettings.h/.cpp` | Schema 未映射进模块 Options，配置形同虚设 |
| 6 | `src/Bootstrap/ConfigRules.cpp` 规则表加一行：差异路径、生效方式、`field<成员指针链>`（ADR-023，2026-11-15 起取代改 `ConfigDiff.cpp`）。必须回答是否实时生效：实时生效写 `applies(应用函数)`，应用函数把新值换进 `LiveSettings` 里对应的活值，模块持 `const Live<T> &`；做不到就写 `restart()`（过渡期的 `notYet` 已于 L2.e 删除，生效方式只有这两种）。面板的字段说明会按这一行自动写“保存后立即生效 / 需重启生效”，`FIELD_HINTS` 等说明表里不要手写生效方式（`PanelServerFixture.PanelHintsLeaveEffectsToRuleTable` 会拦）；面板字段路径与规则表路径不一致时登记 `EFFECT_PATH_ALIASES` | 保存后不报该项变化，用户不知需重启 |
| 7 | 模块 Options 结构 + 组合根装配（`main.cpp`） | 配置读进来却没接线 |
| 8 | 面板 `panel.html` | 通用渲染是兜底；需要专用交互（chips/浮层/联动提示）时要写 custom 分区，并把收集逻辑接进 `collectConfig`；**数组型键还要登记 `ARRAY_PATHS`**（漏了：值被写坏成 null 时渲染成普通文本框，面板再也写不回数组，2026-11-08 `bot.aliases` 实翻车点——该键随后按项目规则改成了单个字符串，登记表现只剩 push 两个白名单键）；**改键的类型**（如 `bot.aliases` 数组→字符串）时，加载器对旧形态要宽容读取并发 Type 警告，骨架、示例、面板提示与依赖该字段的消费方（`BotIdentity` 等）一起改；**策略类配置节（行为策略/实验开关，只在 `.config.json` 手改）登记 `PASSTHROUGH_SECTIONS` 而不是 `SECTION_ORDER`**，面板不渲染但保存时原样带回；**单个不进前端的字段**（如 `bot.aliases`）登记字段级 `PASSTHROUGH_PATHS`（只支持顶层分区的直接子键），同时删掉它在 `SECTION_KEY_ORDER`、`KEY_LABELS`、字段提示里的元数据 |
| 9 | 测试：`ConfigLoader` 默认值/区间、`ConfigTemplateTests`（骨架含该键）、`ConfigRulesTests` 的键数断言（当前 89）与 applies/restart 两份逐键清单、`ConfigReloadTests` 的档位断言、面板往返 | 回归无护栏 |
| 10 | 文档：[卷04](04-配置系统.md) 字段参考 + README 配置节说明 + 涉及行为的 tech-max 卷 | 文档与代码不符 |

自检命令（改完立即跑）：

```bash
cp config.example.json /tmp/check.json && ./build/KleinBot_debug --config /tmp/check.json --check-config  # 未知字段告警须为 0
```

## 7. 加一张 SQLite 表

- 表 DDL 放对应 Store 构造函数（`CREATE TABLE IF NOT EXISTS`，无迁移框架——破坏性变更需自己写迁移或接受删库）。
- 全部 SQL 收在 Store 内；`sqlite3_prepare_v2 + bind + finalize` 三段式，错误 LOG_ERROR + 降级返回（对照[卷13 §1](13-持久化层.md#1-总览一个数据库文件多个独立连接) 的模式）。
- 跨 Store 不共享连接——新 Store 自己 open 同一个 db 文件。

## 8. 改 Agent 行为（系统提示词/循环策略）

- **system prompt 只放稳定内容**；每轮变化的东西必须走 `appendContextNote`（尾插）或 `attachRecallContext`（前插）——动了 system 就作废全部前缀缓存（Anthropic 断点布局也会失效，[卷11 §6](11-模型调用层.md#6-anthropicstandard-差异点anthropicstandardcpp)）。
- 工具循环上限 `max_tool_rounds` 定义于 ChatService.h；收尾策略必须保持"尾部 user 注记"方案，不得回退为"清空 tools"。
- 新的终态语义用 ToolResult 的 terminal/suppress_text_reply/outbound_messages 表达，不要在 ChatService 里特判工具名。
- 能决定她说话风格、又因人而异的内容（关于她自己的事实、语气）不写进可执行文件，做成部署者文件（`source/soul.md`、`source/facts.md`；项目规则 2026-11-16）。代码里只放格式与机制，例如事实卡 `Affect/FactsCard`：部署者事实这种稳定文本进 system，现场事实这种每轮都变的进 user 侧尾部（ADR-026）。
- 群聊材料的一行只经 `Perception/GroupLineFormat::formatGroupLine` 格式化（ADR-026）；要改行格式（时刻、发言人、回复关系）只改这一处。

## 9. 提交前自检表

| 检查 | 依据 |
| --- | --- |
| 业务模块 include `Configuration/` 或读取 JSON | 架构测试失败 |
| 业务模块 include `Bootstrap/`（只有 `main.cpp`、`Bootstrap`、`WebUI` 可以） | 架构测试失败（ADR-023） |
| SQL 没漏出 Store | 同上（review 目视） |
| 没在业务层拼 OneBot/CQ 字符串 | 出站只发 OutboundMessage |
| 供应商 JSON 细节没进 ChatService | 只认统一 DTO |
| 长生命周期对象在 main 创建、引用注入 | 组合根纪律 |
| 新线程观察 `running`、可被 shutdown join | 退出链完整 |
| 外部 HTTP 挂了 CurlRequestControl | 优雅退出不卡死 |
| 外部内容（网页/搜索）声明不可信 | 提示注入防线 |
| 单用户状态操作都过 USS 锁 / Store 锁 | 并发安全 |
| 敏感值（key/token）不进日志、不进 diff | 安全规则 |

## 10. 调试手段

| 观察目标 | 获取方式 |
| --- | --- |
| 模型往返原文 | Debug 构建 + LOG_DEBUG（OpenAI/Anthropic 适配器记录"返回的原始消息"——**含用户内容，生产环境不建议长期开启**） |
| 消息路由决策 | 控制台 `[type]user:plain` 行（Message.cpp:61） |
| 工具执行 | "工具 X 完成，回灌 N 字符" INFO |
| 记忆提取 | "长期记忆已更新，用户：…，条目数：…" INFO；提取失败 WARNING 带返回码 |
| 配置诊断 | 启动日志的 configSeverity 输出 |
| 调度器 | 启动 INFO"消息执行器线程：初始/最大/队列容量"；队列满 WARNING |
| SQLite | 直接 `sqlite3 source/.conversations.db` 查[卷13 §2](13-持久化层.md#2-全库-20-张表-ddl-汇总) 的表 |
| 面板 | `Cache-Control: no-store`，改 panel.html 刷新即生效 |

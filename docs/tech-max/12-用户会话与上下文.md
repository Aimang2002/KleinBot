# 卷 12 · 用户会话与上下文管理：UserSessionService

> 源码基准：`src/UserSession/UserSessionService.h/.cpp`（506 行，含头文件）、`src/Message/Person.hpp`。USS 管着"每个用户的内存画像"：历史镜像、人格、模型、语音开关，以及全项目最精巧的**上下文水位裁切算法**（token 水位 + 滚动摘要）。

## 1. 职责与数据

```cpp
class UserSessionService {
    std::mutex mutex_message;                                    // 唯一一把锁（所有方法）
    std::unique_ptr<std::unordered_map<uint64_t, Person>> user_messages;  // QQ → Person（惰性创建）
    const ModelRegistry &registry;                               // 模型查找
    const Live<ChatOptions> &chatOptions;                        // chat 组配置的活值（ADR-023，L1.a）：每次操作开头取快照
    const Live<BotIdentity> &bot;                                // 机器人身份的活值（L2.d）：建用户、内置默认人格与摘要里她的发言人标签取当前名字
    std::string soul_file = "source/soul.md";
    ConversationStore &store;
    MemoryService *memoryService = nullptr;      // 组合根后置注入（构造顺序需要）
    ImageAssetStore *imageAssetStore = nullptr;  // 同上
};
```

Person（[卷07 §6](07-消息调度与路由.md#6-person-结构personhpp卷12-详述)）：全量历史镜像 + `history_anchor`（裁切锚点）+ 滚动摘要 + 人格 + 手动选的模型（`std::optional`，空 = 跟随默认模型）+ 语音开关。原先建用户时拷进 Person 的三个超参（`temperature`/`frequency_penalty`/`presence_penalty`）从未被读取，L1.a 删除。

**锁的使用纪律**：`mutex_message` 保护用户 map 与每个 Person 的内部状态；`ensureUserExistsUnlock` 是所有公开方法的公共前缀（取得锁后首先保证目标用户已初始化）。

## 2. 用户创建（ensureUserExists / createDefaultPerson）

首次遇到用户时：

```
system_prompt = store.loadPersona(user)          // ① 持久化人格（#设置人格 的结果）
                非空 ? 它 : loadSoulFallback()    // ② soul.md；文件缺失/空 → 内置中文默认 + WARNING
current_model 留空                               // 空 = 跟随当前默认模型（见下文“默认模型跟随”）
user_chatHistory = store.loadFrom(user, store.contextStartId(user))
                // ★ 冷启动只读回"上下文起点之后"的消息（轻重置边界，见 §5）
```

**默认模型跟随**（2026-11-15 L1.a，项目规则：默认模型改了老用户跟）：`Person::current_model` 是 `std::optional<std::string>`，只有 `#切换模型`（`switchModel`）写它。实际用哪个模型一律经 `resolveModelName(person, chat)`（`UserSessionService.h`，`current_model.value_or(chat.defaultModel)`）解析，`buildChatRequest` 与 `getModelName`（`#查询模型`、`get_current_model` 工具经它）都调这一个函数，chat 取本次操作开头的活值快照。于是没手动选过的用户——包括默认模型改动之前就存在的——在默认模型重载后的下一次请求就跟上；手动选过的保持自己的选择。手动选择只在内存，重启后恢复跟随默认（与此前“重启回默认”一致）。新默认模型不在注册表里时沿用原有报错路径（`buildChatRequest` 返回空，上层回“当前模型未注册”）。

`soul.md` 每次兜底都**重读文件**（不缓存）——管理员改默认人格后，用户 `#人格还原` 无需重启即生效。内置兜底为 `"你是<bot.name>，部署者的AI助手。"`，2026-11-15（L2.d）起按当前名字现拼（成员 `default_personality` 删除）：每个要建用户的公开方法在拿 `mutex_message` 之前取一次名字快照，往下传给 `ensureUserExistsUnlock`/`createDefaultPerson`/`loadSoulFallback`，滚动摘要里她的发言人标签用同一次的快照；文案不变。

**服务契约包裹（D13，T5）**：`buildChatRequest` 装配时在人格之后固定追加 `kServiceContractFrame`（"助手优先、人格其次"——专业/任务诉求严谨用工具，闲聊按人格自由表达，模型按每条消息自适应语域）。契约归代码、人格归 soul.md；`#设置人格` 的自定义人格同样被包裹（system_prompt = 人格 + 契约，拼接发生在 buildChatRequest 而非存储层，user_persona 表内容不含契约）。

**部署者事实不在这里装配（经历层 E0，ADR-026）**：`source/facts.md` 与 `soul.md` 同目录，但不经 USS、不进 `Person.system_prompt`。它只在群聊两条路径、`affect.enabled` 为真时由调用方追加在 system 尾部（会话轮的契约开头、@ 回复的群聊收敛契约之后），每次现读，改了下一次请求即生效；私聊不加。

**人格编译（D14，T5；已于 2026-09-18 整链路移除）**：v2.4.1 曾实现"soul.md 经 LLM 编译为标签压缩式 prompt"——四个入口（冷启动/`#重置对话`/`#重置上下文`/`#人格还原`）置位 `Person.persona_needs_build`，首次聊天经 `buildOnce` 编译、共享缓存按 (规范+soul) 哈希寻址单飞复用。真机证伪后拆除（激活词丢频率/条件限定、冷门角色无行为簇可激活、产物内存态不可检视），`persona_needs_build`、共享缓存、单飞与 `PersonaBuildTests.cpp` 一并移除。**现行行为**：`createDefaultPerson`/`resetContext`/`resetPersonality` 直接以手动人格或 `loadSoulFallback()`（每次现读 soul.md）作为 system_prompt，无编译调用；`memories` 以对话轮次为源、与 system_prompt 正交的关系不变。

## 3. appendMessage——write-through 的唯一写入口

```cpp
int64_t appendMessage(user_id, role, content) {
    加锁 { ensureUser; ts=now;
        history.push_back({role, content, ts});           // ① 先内存
        id = store.append(user_id, role, content, ts);    // ② 再库（失败返回 0，内存不回滚）
        history.back().id = id;                           // ③ SQLite 自增 id 回填镜像
    }
    return id;
}
```

- 内存与 SQLite 在**同一把锁内**先内存后库 = write-through（库失败时内存保留、id=0——记忆溯源证据能力下降，但聊天不中断）。
- id 的用途：轻重置算边界、`#删除上条对话` 删尾部、记忆 source 区间、图片关联。

## 4. buildChatRequest——token 水位裁切与滚动摘要

2026-11-08 起水位按 token 计量（取代 40/20 条），被移出窗口的原文压成"早前对话摘要"。不新增配置键，摘要不落库。

```cpp
std::optional<ChatCallBundle> buildChatRequest(user_id, bool trimWindow = true) {
    chat = chatOptions.get();                       // 本次装配的配置快照，在业务锁外取（L1.a）
    加锁 { ensureUser; Person &p = …;
        model_name = resolveModelName(p, *chat);     // 手动选的或当前默认模型
        modelPtr = registry.find(model_name);         // null → nullopt（上层提示"模型未注册"）
        bundle.model/model_name/system_prompt = …; 超参取 chat 快照;
        // ↓ 裁切（不回写 user_chatHistory，原始历史保持完整）
        filtered = [m for m in p.user_chatHistory if m.timestamp + survival >= now];  // ① 时间过滤
        p.history_anchor = min(p.history_anchor, filtered.size());   // ② 夹紧（撤回/过期收缩后下标仍合法）
        bundle.digest_before = p.context_digest;
        if (trimWindow) {
            window = est(digest) + Σ est(filtered[anchor…end]);      // utils::estimateTokens
            if (window > kContextHighTokens /*32000*/) {             // ③ 越过高水位才跳
                cut = 最小下标 使 est(digest) + Σ est(filtered[cut…end]) ≤ kContextLowTokens /*16000*/;
                cut = min(cut, 末条);                                // 末条单独超低水位也保住
                cut 落在 assistant → 后挪到下一条 user（后面没有 user 则不挪）;
                bundle.evicted_lines = filtered[anchor…cut) 每条一行 "用户: …" / "<bot.name>: …"（换行折成空格）;
                p.history_anchor = cut;
            }
        }
        bundle.request.history = filtered[anchor … end];             // ④ 窗口 = 锚点之后全部
    }   // 锁在返回前释放——HTTP 与 worker 调用期间不持锁
}
```

- 常量 `UserSessionService::kContextHighTokens = 32000`、`kContextLowTokens = 16000` 是公开静态成员（测试直接引用）。token 用 `utils::estimateTokens` 启发式估算（CJK 1/字、ASCII 1/4 字符，[卷18](18-支撑模块.md)），与群会话轮的材料预算同一实现。
- `trimWindow=false` 只给 `ChatService::replyInCharacter`/`requestInCharacter` 用：这两条路径自带 history、会丢弃窗口，若在这里前移锚点，被移出的那段就永远进不了摘要。
- **滚动摘要**（`Person::context_digest`）：`buildChatRequest` 只产出 `evicted_lines` 和摘要快照，不调模型。`ChatService::reply` 在锁外用 `mergeDigest(worker, kPrivateChatDigestSystem, 旧摘要, evicted_lines)`（`Application/ContextDigest`，与群会话轮共用）合并，成功则 `setContextDigest` 写回，并经 `attachDigestContext` 前插到本轮最后一条 user 消息（与召回证据同一注入点，位于召回块之前）。失败或未注入 worker 时保留旧摘要，被移出的那段丢弃，即 2026-11-08 之前的行为。摘要只在内存，2026-11-08 决定不落库（落库需要给会话表加列，待议），重启即空。

### 为什么必须"跳变"而不是滑窗（前缀缓存经济学）

供应商（OpenAI 自动 / Anthropic 显式断点）按**请求前缀逐字节匹配**缓存。若每轮滑动一条，头部每变一次就是一次全量 miss。

```
跳变式（当前实现）：
  窗口（含摘要）≤32K token 时锚点不动 → 头部逐字节稳定 → 增量命中
  越过 32K → 锚点一次跳到"到末尾 ≤16K" → 付一次全量 miss → 之后约 16K token 的对话又稳定
滑窗式：每一轮头部都变 → 每轮全量 miss
```

摘要注入在**最后一条 user 消息**（每轮本就变化的尾部），不进 system 也不改窗口头部，所以不破坏前缀缓存。摘要只在锚点移动那一轮更新。

按 Anthropic 计价建模（命中 0.1x、写入 1.25x）：滑窗稳态约为全价的 92%，锚点水位平均约 29%，相差约 3.2 倍；而且窗口有上限时，累计成本低于"从不截断"（前缀无限增长时，每轮的缓存读取费线性上涨）。

**锚点必须持久在 Person 里**：若每次按"存活总量是否超限"重新判断，完整历史只增不减，首次截断后每轮都会重新触发，退化成滑窗。时间过滤只作用于"缓存本来就冷"的场景（供应商 TTL 只有几分钟），不构成额外损失。

其他细节：窗口以 user 消息开头，但不保证 tool 调用结构完整（会话镜像里只有 user/assistant 文本）；`timestamp+survival<now` 的消息丢弃（`message_survival_seconds` 默认 3600，取本次快照，重载后下一次装配即按新值）；过期收缩时只夹紧锚点，不产出 evicted_lines。

## 5. 三种重置/删除语义（精确对照表）

| 操作 | 内存镜像 | SQLite conversations | 长期记忆 | 图片 | 上下文起点 | 人格/模型/语音 |
| --- | --- | --- | --- | --- | --- | --- |
| `#重置对话` resetChat | 清空 + anchor=0 + 摘要清空 | **保留** | 保留 | 保留 | **= 最后一条消息 id + 1** | 保留 |
| `#重置上下文` resetContext | 清空 + anchor=0 + 摘要清空 | **全删** | **clearUser 全删** | **clearUser 全删** | = 0 | 保留 |
| `#删除上条对话` removePreviousContext | 删最后一轮（摘要不动） | removeLast(同条数) | removeBySourceFrom(首删id) | removeByConversationFrom | 不动 | 不动 |
| `#人格还原` resetPersonality | 清空 + anchor=0 + 摘要清空 | **保留**（user_persona 删行） | 不动 | 不动 | **= 最后一条消息 id + 1** | 重读 soul.md + 待编译 |

resetChat 的关键设计：起点设为"镜像最后一条 +1"而非"库里最后一条 +1"——镜像永远等于库在起点之后的后缀，因此两者等价；之后冷启动 `loadFrom(start)` 读回空，旧话题行留在库里**仅供召回检索**。轻重置后 `#删除上条对话` 只会作用于新话题（镜像为空时返回"没有上下文！"），不会越过边界回删。`#人格还原` 的上下文半边与 resetChat 同语义（人格切换即新对话起点，旧人格口吻的上下文不压在新人格上），人格半边是删 user_persona 行 + 重读 soul.md + 重新武装编译（D14 第四入口）。

## 8. 并发模型

- **同一用户**的消息任务被调度器串行（[卷07](07-消息调度与路由.md)），所以 USS 方法对该用户无并发；**不同用户**并发进入时由 `mutex_message` 串行化——锁粒度是"全表"，聊天路径持锁时间 = 内存操作 + 一条 SQLite INSERT（busy_timeout 5s）。
- `buildChatRequest` 返回**值拷贝**，模型 HTTP 的数秒期间不占锁——这是"响应不互相阻塞"的关键设计。
- chat 活值的快照在 `mutex_message` 之外取（`buildChatRequest`、`getModelName` 都先取快照再加锁），活值的锁不与 USS 锁嵌套；一次装配只用这一份快照，重载与它并发时这次装配仍是旧值，下一次装配才是新值（L1.a）。
- `history_anchor` 在 buildChatRequest 里被**原地修改**（Person 是共享状态，锚点前进即刻生效于下轮）。
- 摘要合并（杂务模型，20 秒超时）在 ChatService 里、USS 锁外进行，结果经 `setContextDigest` 持锁写回；同一用户的任务由调度器串行，合并期间不会有同用户的另一轮插入。不新增线程。

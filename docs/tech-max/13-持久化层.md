## 1. 总览：一个数据库文件，多个独立连接

`storage.conversation_database`（默认 `source/.conversations.db`，点前缀隐藏，旧路径无自动迁移）被 **9 个 Store 各自打开独立连接**（ConversationStore / MemoryStore / ReminderStore / ImageAssetStore / PerceptionStore / GroupContextStore / GroupListService / DecisionStore / KnowledgeLedger——后五者按观察通道或 `affect.enabled` 条件构造或打开），各自持独立 mutex。同一文件多连接 + WAL 是安全的（busy_timeout 5s 处理偶发写冲突）。

通用初始化模式：构造函数先 `utils::ensureParentDirectories(dbPath)` 自建父目录（首次部署 `source/` 不存在时，Windows 上 `sqlite3_open` 会报 unable to open database file 而退化成仅内存——2026-09-19 真机首跑暴露后修复）；`sqlite3_open` 失败 → LOG_ERROR + `db=nullptr`（降级模式）；`busy_timeout(5000)`；`PRAGMA journal_mode=WAL`；`CREATE TABLE IF NOT EXISTS …`（无 schema 版本表/迁移框架——DDL 只做最低兼容初始化）。

**降级语义**（所有 Store 一致）：db==nullptr 时写入 no-op（返回 0/false）、读取空结果，全部 LOG_ERROR。聊天不因数据库故障中断。

`DecisionStore`（`src/Affect/`）在 `affect.enabled=true` 时构造，与其余 Store 共用同一个数据库文件：`appendDecision/Execution/Feedback` 均 `INSERT OR IGNORE`（主键幂等），查询提供 `findDecision`/`recentDecisions`/计数；决策先校验 `BehaviorPlan`（schema_version/action/tool_policy/allowed_tools），计划以 JSON 落 `plan_json`。M1 只记录影子决策，不改变回应；执行状态 `queued` 只表示已交给出站队列，R0.2（2026-10-28）起由传输层回执推进为 `sent`/`failed`/`unknown` 并回填真实 `outbound_message_id`，B2 关闭。

`PerceptionStore` 只有 `upsertBatch` 一个写方法：`INSERT ... ON CONFLICT(user_id, group_id) DO UPDATE` 计数累加（不是覆盖），单事务批量提交；写只来自 pollingThread 的 `PerceptionChannel::flushDue`（30s 或累计 delta≥100 节流）。`GroupContextStore` 以内存 deque 镜像为读路径（选择打分零 SQL），write-through 落 `group_messages`，条数淘汰随 append、TTL 清理由 pollingThread 周期 `prune`；另维护 `engagement_cold` 表（2026-09-17 起）：冷启动自学习状态每群一行（hourly_ema/armed_ts/day_anchor/cold_today/cooldown_until），启动整表读入、状态变更 UPSERT（EMA 采样/当日帽变动/会话结束冷却），无 TTL，重启续用。`GroupListService` 是观察通道运行状态的唯一所有者（项目规则 2026-09-15）：`perception_meta.feature_enabled` 为总开关、`group_cache.monitored` 为每群监控状态（0/1），配置体系没有对应键，面板改动直接落库并**即时生效**。启动即从两处重建状态与群列表镜像（OneBot 未握手也有数据），就绪后 `get_group_list` 整表覆写并降频为日级刷新；刷新时 `monitored` 由内存监控集重新派生，不被协议端数据冲掉。不在机器人群列表内的群号（手动输入）也落一行以保存监控意图。观察通道的功能行为（滑窗/隐私边界/话题会话）见 technical-design §10.8。话题会话（EngagementService，意志层 v2）的会话/摘要/召回预算状态是**纯内存**（重启即失），不新增表；消息原文仍在 `group_messages`。

## 3. ConversationStore 逐方法

| 方法 | SQL 语义 | 备注 |
| --- | --- | --- |
| `append(user,role,content,ts)` | INSERT，返回 `last_insert_rowid` | 失败 0（内存模式） |
| `loadAll(user)` | `WHERE user_id=? ORDER BY id ASC` | 召回/审计用 |
| `loadFrom(user,startId)` | `… AND id>=startId ORDER BY id ASC` | **冷启动入口**（起点= context_state） |
| `contextStartId(user)` | SELECT 单行 | 无记录=0（全量加载） |
| `setContextStartId(user,startId)` | upsert（负值钳 0） | 起点变化不删行 |
| `loadPersona/savePersona/clearPersona` | user_persona 三件套 | save=upsert |
| `search(user,keyword)` | 兼容壳：`searchMany({keyword},30)` 后按 id 升序 | |
| `searchMany(user,queries,limit,excludeId)` | 多短语 LIKE 检索（[§4](#4-searchmany原始历史的检索算法282342-行)） | 召回主路径 |
| `loadByIdRange(user,start,end,padding=1)` | `id BETWEEN max(1,start-pad) AND end+pad ORDER BY id ASC` | 记忆证据回取；start/end 自动交换、非法(≤0)返回空 |
| `clearUser(user)` | DELETE conversations | resetContext 用 |
| `removeLast(user,count)` | 尾部 count 行删除，**返回首删 id**（MIN(id) of tail） | 两步 SQL：先 SELECT MIN 再 DELETE IN 子查询 |

## 4. searchMany——原始历史的检索算法（282–342 行）

```
plan = buildRecallQueryPlan(queries)         // TextRecall 的 n-gram 计划（卷14 §5）
plan.terms 空 → 返回{}
candidateLimit = max(30, limit*8)
对每个 term：
    SELECT … WHERE user_id=? AND (?=0 OR id<>excludeId) AND content LIKE '%term%' ESCAPE '\'
         ORDER BY id DESC LIMIT candidateLimit
    每命中行：relevance = scoreRecallText(plan, content)
    按 id 去重（map[id]），保留 relevance 更高的版本
排序：relevance 降序，同分 id 降序；截断 limit
```

- `escapeLikePattern` 转义 `%`/`_`/`\`（防通配注入）。
- excludeId 用于自动召回排除"当前问题自己"。
- 检索面是 **content 原文**（含图片占位符）；召回排序与 MemoryStore.search 共用同一评分函数——三类候选可比。

## 5. ReminderStore 逐方法

insert（返回自增 id）、listForUser（trigger_at ASC, id ASC）、countForUser、loadPending（全表 trigger_at ASC）、deleteById（`sqlite3_changes>0` 判定是否实际删除）、updateTrigger。均为简单 SQL，无特殊逻辑；调度语义在 ReminderService（[卷15](15-提醒系统.md)）。

## 6. 并发与一致性模型

| 层 | 锁 | 说明 |
| --- | --- | --- |
| ConversationStore | 自身 dbMutex | 但主要调用方 USS 已在会话锁内 → 双重串行（安全，稍冗余）；**MemoryService 的 searchMany/loadByIdRange 从记忆线程直接调用**，靠 dbMutex 保证安全 |
| ReminderStore | dbMutex | 定时线程与消息 worker 并发访问 |
| MemoryStore | dbMutex | 记忆 worker 与召回调用并发 |
| ImageAssetStore | mutex | 多 worker 并发导入图片 |
| DecisionStore | 自身 mutex | @ worker 与群 lane 并发记录决策/执行；单连接串行化 |

WAL 模式 + 5s busy timeout 下，跨连接写冲突表现为偶发等待而非失败。

已知一致性边界：多表操作（如 clearUser 删 conversations + context_state + …）**不在同一事务内**——进程在两步之间崩溃可能留下部分删除（概率极低，属已接受的设计取舍）。

## 附：affect_executions 回执回填与 group_messages 自消息回填（R0.2，2026-10-28）

- `DecisionStore::updateExecutionReceipt(execution_id, status, outbound_message_id)`：`unknown` 只推进 `queued`；`sent`/`failed` 推进 `queued` 与 `unknown`；状态已定（sent/failed）不再改动；空 `message_id` 不擦掉已有值。`findExecution` 供测试/排查读回。
- `affect_executions.outbound_message_id` 是**逗号分隔列表**（分段投递：首段在前，后续段由 `appendExecutionMessageId` 追加、去重）；`findExecutionByOutboundMessageId` 用 `instr(','||列||',', ','||?||',')` 精确命中任一段。
- 调用顺序约束：**先 `recordExecution` 再投递**（`Message` 与 `EngagementService` 已调序），否则回执可能先于行到达而丢失。
- `affect_feedback.source` 取值新增 `manual_admin` / `manual_user`（R0.3，按标注人分管理员与网友；confidence 1.0 / 0.6）；`DecisionStore::feedbackFor(decisionId)` 读回。
- `DecisionStore::findExecutionByOutboundMessageId` / `latestExecution(groupId,userId,since)`（R0.3）：人工反馈定位；后者 JOIN decisions，群按 `group_id`、私聊按 `group_id=0 AND user_id`，排除 `skipped`。
- `GroupContextStore::backfillMessageId(correlation_id, message_id)`：按内存镜像中自消息的 `correlationId`（仅内存，不落库）定位行，更新镜像与 `group_messages.message_id`。无表结构变化。

- `rollbackTo(at)` / `rollbackBefore(run_id)` 只追加 `rollback` 行（evidence 记 `to`、`to_version`、`restored_origin`），那时不存在的记 `withdrawn`；`applyDecay()` 追加 `fade`/`decay` 行；规模上限（每 `(kind, scope_group, scope_user)` 至多 200 条 active）追加 `fade`/`decay` 行，evidence `{"reason":"scope_limit"}`。
- `forgetPerson(user)` / `forgetGroup(group)` 连同历史 DELETE（同 `MemoryStore::clearUser`），由 `#清除认识` 调用；`#重置上下文` 不涉及账本。
- `DecisionStore::feedbackExists(feedback_id)`（只读，新增）给依据核对器用。

```sql
CREATE TABLE IF NOT EXISTS affect_knowledge (
    id INTEGER PRIMARY KEY AUTOINCREMENT,      -- 编号（命令里写 #编号）
    kind TEXT NOT NULL,                        -- habit / group / person
    scope_group INTEGER NOT NULL DEFAULT 0,    -- 0 = 全局
    scope_user INTEGER NOT NULL DEFAULT 0,     -- 只有 person 非 0
    key TEXT NOT NULL,
    text TEXT NOT NULL,                        -- 一句认识（≤ 80 码点）
    search_text TEXT NOT NULL DEFAULT '',      -- 检索词（≤ 120 码点，E4 取用用）
    strength REAL NOT NULL,                    -- 0–1，存储值；取用看有效强度
    status TEXT NOT NULL,                      -- active / faded / withdrawn
    version INTEGER NOT NULL,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,
    last_confirmed_at INTEGER NOT NULL,
    UNIQUE(kind, scope_group, scope_user, key));
CREATE INDEX IF NOT EXISTS idx_affect_knowledge_scope ON affect_knowledge(scope_group, scope_user, status);
CREATE TABLE IF NOT EXISTS affect_knowledge_history (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    knowledge_id INTEGER NOT NULL,             -- affect_knowledge.id
    version INTEGER NOT NULL,
    text TEXT NOT NULL,                        -- 这一版的结果状态
    search_text TEXT NOT NULL DEFAULT '',
    strength REAL NOT NULL,
    status TEXT NOT NULL,
    change TEXT NOT NULL,                      -- add / modify / strengthen / weaken / fade / withdraw / rollback
    origin TEXT NOT NULL,                      -- reflection / teaching / decay / rollback
    evidence_json TEXT NOT NULL DEFAULT '{}',  -- 依据 id、by、why、回滚的 to / to_version / restored_origin
    run_id TEXT NOT NULL DEFAULT '',
    created_at INTEGER NOT NULL);
CREATE INDEX IF NOT EXISTS idx_affect_knowledge_history_entry ON affect_knowledge_history(knowledge_id, id);
CREATE INDEX IF NOT EXISTS idx_affect_knowledge_history_run ON affect_knowledge_history(run_id);
```
